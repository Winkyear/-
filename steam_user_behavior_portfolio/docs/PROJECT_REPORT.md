# Steam 用户行为与内容运营分析项目报告

## 一、项目背景与业务目标

Steam 用户经常拥有大量游戏，但“已拥有”不等于“已启动”。内容运营团队需要回答两个问题：哪些用户最值得做已有内容召回，哪些游戏应该进入推荐与激活资源位。

项目将 20 万条购买/游玩行为与 2.7 万款商店元数据结合，构建用户、游戏和类型三层指标体系。由于数据没有时间、订单金额、推荐曝光和实验分组，本项目只做横截面行为分析，不计算留存、流失、收入或 LTV，也不把关联写成因果。

## 二、数据收集与清理

### 数据来源

- 主表：和鲸社区“包含用户行为的 Steam 游戏数据集”，文件 `steam-200k.csv`。
- 补充表：和鲸社区“Steam 商店游戏数据集”，使用其中 `steam.csv`。
- 两个本地文件的字节数与和鲸元数据完全一致，SHA-256 见 `source_info.md`。

### 清理动作

1. 为无表头行为数据补充 `user_id / game_name / behavior / value / aux` 字段。
2. 删除 707 条完全重复记录。
3. 校验行为类型只有 `purchase` 与 `play`，购买值均为 1，游玩时长均大于 0，辅助列均为 0。
4. 在 `user_id × game_name` 粒度聚合，购买转为二元标记，游玩时长求和。
5. 游戏名只做大小写折叠、空白压缩和商标符号清理，再与商店表精确连接。未使用模糊匹配。
6. 商店表解析发行年份、主类型、好评率、所有者区间中点与价格带。
7. 构建样本筛选口径：若某个内容名在全样本从未出现 `play`，标记为 `observed_playable = 0`。该标签由结果数据派生，只用于灵敏性分析，不等同于官方 DLC 或可独立启动分类。

### 数据质量结果

- 行为原始记录：200,000 条；清理后 199,293 条。
- 用户：12,393 名；游戏名称：5,153 个。
- 商店元数据只精确匹配 48.47% 的购买关系、46.28% 的游戏名称；类型、价格与发行商分析只覆盖该子样本。
- 1,555 个内容名从未出现游玩记录，占 8.78% 的拥有关系。其中可能包含 DLC、工具类内容或真实零启动游戏，现有数据无法官方核验。

## 三、指标体系

### 核心结果指标

- 样本筛选共现率 = 已出现正游玩时长的用户-游戏关系数 ÷ `observed_playable = 1` 的拥有关系数。
- 筛选后未启动关系数 = `observed_playable = 1` 的拥有关系数 − 已启动关系数。
- 总游玩时长 = `play` 行的小时数合计。

### 诊断指标

- 用户层：样本筛选游戏库规模、已启动游戏数、用户启动率、累计游玩时长。
- 游戏层：购买用户数、已启动用户数、游戏启动率、总游玩时长、内容象限。
- 结构层：Top 10/Top 1% 游玩时长占比、单一购买用户游戏占比、主类型贡献。
- 质量护栏：元数据匹配率、样本量阈值、非独立游玩候选标记。

## 四、数据分析与主要发现

### 1. 样本筛选后仍有 47,018 个关系没有出现正游玩时长

全部 128,801 个拥有关系中，70,474 个出现过正游玩时长，静态共现率为 54.72%。排除全样本从未出现 play 的内容名后，分母为 117,492 个，样本筛选共现率为 59.98%，对应 47,018 个未启动关系。

两个口径相差 5.27 个百分点。这可以作为数据产品的灵敏性对照，但不能直接将差异归因于 DLC；正式上线前应用 appid 与官方内容类型字典重算。

### 2. 24.56% 的用户属于“大库低启动”层

规则分层使用样本筛选游戏库、用户启动率与累计游玩时长的分位数：

- 大库低启动：3,044 人，占 24.56%；平均样本筛选游戏库 32.83 款，用户级启动率简单平均 55.39%。
- 深度活跃：930 人，占 7.50%；平均启动率 100%，累计游玩时长均值 766.38 小时。
- 轻量用户：2,225 人，占 17.95%；平均样本筛选游戏库约 1 款，累计游玩时长均值 0.43 小时。
- 常规玩家：6,194 人，占 49.98%；平均启动率 80.60%。

“大库低启动”用户既有较大的可召回内容池，又已经表现出较强的总体游玩意愿，是历史行为层面的优先实验对象。没有实验数据，尚不能确认其对召回动作的增量响应一定最高。

### 3. 游玩时长向头部内容集中

- Top 10 时长榜游戏贡献 58.18% 的总游玩时长，Top 10 购买榜游戏贡献 12.09% 的拥有关系；两个榜单不是同一组游戏。
- Top 1% 游戏贡献 77.60% 的总游玩时长和 26.93% 的拥有关系。
- 22.71% 的游戏只有 1 名购买用户，内容长尾明显。

未截尾累计时长明显向头部集中，但正时长 pair 的中位数、P99 与最大值差异很大，因此 58.18% 只作为未截尾分布描述。长尾高启动内容可进入小流量探索池，但必须用增量启动和后续游玩验证。

### 4. 类型结论只能用于方向性筛选

在精确匹配样本中，Action 主类型贡献 84.44% 的游玩时长，Strategy 和 Indie 分别贡献 5.33% 和 3.87%。该结果受到匹配覆盖和头部游戏结构影响，不能代表完整 Steam 市场类型偏好。

## 五、业务痛点与建议

### 痛点一：口径混淆会高估未启动问题

对象：数据产品与运营分析。

动作：在经营看板同时展示全量静态共现率和样本筛选共现率，内容页保留筛选器，允许追溯被排除名称。

验收：两张聚合表的购买与游玩关系数残差均为 0；看板明示口径说明，不把样本筛选标签宣称为官方 DLC 分类。

### 痛点二：大库用户存在较多未启动内容

对象：用户召回与站内推荐。

动作：针对“大库低启动”用户，用最近未玩、历史同类型深度游玩、好评率等特征生成 3–5 款已有游戏推荐。先做随机对照实验，不直接全量上线。

验收：14 天内已有游戏首次启动率作为主指标；7 天累计游玩时长作为质量指标；退订或负反馈作为护栏。实验前需补齐触达时间、曝光、点击与启动时间。

### 痛点三：长尾内容发现效率不明

对象：内容推荐策略。

动作：从长尾高启动游戏中按样本量、好评率和用户偏好筛选候选，拿出固定小比例探索流量，与头部保守推荐对照。

验收：比较每千次曝光带来的增量启动、7 天游玩时长与覆盖游戏数；至少运行两个完整周并进行分层随机化。

## 六、工具链与交付

- Python / PyCharm / Anaconda：清洗、聚合、分层、可视化与 SQLite 落库。
- SQL：核心指标、用户分层、内容象限、长尾结构与质量对账查询。
- Excel：可编辑经营看板、分层与内容明细。
- Power BI Desktop：星型模型、DAX 指标与三页仪表盘搭建说明。
- PowerPoint：面向面试与业务汇报的完整故事线。
- HTML：按 data-analysis skill 六段式生成的自包含正式报告。

## 七、后续数据补齐

1. 事件时间与首次拥有时间：验证 14/30 天启动、留存与召回窗口。
2. 推荐曝光、点击、排序位与实验分组：评估策略增量，而不是历史相关。
3. 商品类型与 DLC 关系：替代当前基于“是否出现过 play”的保守可玩性规则。
4. 订单金额、折扣、退款和地区：构建净收入、价格弹性与 LTV。
5. 版本、活动和客户端状态：区分内容问题、技术问题与活动期结构变化。
