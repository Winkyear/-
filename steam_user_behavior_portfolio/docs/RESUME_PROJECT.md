# 简历项目经历写法

## 项目名称

Steam 用户行为与内容运营分析 | Python、SQL、Excel、Power BI

## 简历版（建议放 3–4 条）

- 基于和鲸社区 Steam 用户行为与商店元数据，使用 Pandas/NumPy 清洗 20 万条行为记录，去除 707 条完全重复数据，并在用户-游戏粒度构建 12,393 名用户、5,153 款游戏的分析宽表与 SQLite 数据库。
- 设计静态共现率、筛选后未启动关系数与内容时长集中度指标，对比全量口径 54.72% 与样本筛选口径 59.98%，定位 47,018 个待进一步核验的用户-游戏关系，并明确披露循环口径风险。
- 基于游戏库规模、启动率与累计时长完成可解释用户分层，定位 3,044 名“大库低启动”用户，占 24.56%，并形成已有内容召回的 A/B 实验方案与指标护栏。
- 使用 SQL、Excel 与 Power BI 模型拆解内容结构，发现未截尾口径下时长榜 Top 10 游戏贡献 58.18% 的累计游玩时长，并将极端值敏感性与元数据覆盖不足写入决策边界，输出可复跑 Python 工程、DAX、经营看板与业务汇报 PPT。

## 面试口述版（约 90 秒）

这个项目解决的是 Steam 平台“用户已经拥有游戏，但未必真正启动”的内容运营问题。我从和鲸社区取得 20 万条购买和游玩时长记录，并补充 2.7 万款 Steam 商店元数据。清洗时我发现 1,555 个内容名在全样本从未出现 play，其中可能混有 DLC、工具类内容和真实零启动游戏。因为没有官方可玩性标识，我没有直接归因，而是建立全量与样本筛选两套口径做灵敏性对照，共现率分别是 54.72% 和 59.98%。

随后我在用户-游戏粒度构建事实表，按可玩游戏库规模、用户启动率和累计时长做规则分层。24.56% 的用户属于“大库低启动”，平均有 32.83 款可玩游戏，启动率 55.39%。内容侧则发现 Top 10 游戏贡献 58.18% 的总游玩时长，说明消费高度集中。我没有把这些关联直接写成策略效果，而是提出对“大库低启动”用户做已有游戏召回实验，并用 14 天首次启动率、7 天游玩时长和负反馈做主指标与护栏。

最终我交付了 Python 清洗分析脚本、SQLite 与 SQL 查询、Excel 看板、Power BI 的 DAX 和建模说明，以及业务汇报 PPT。这个项目最重要的部分不是图表，而是把“样本筛选”与“官方内容类型”区分开，再把静态分析结果落到可验证的实验设计。

## 可能追问与回答要点

### 为什么不用聚类？

本项目的动作是召回与内容激活，需要规则清楚、容易部署和解释。数据又没有时间窗口，聚类稳定性难验证，因此采用分位数规则分层，并把后续实验作为效果验证。

### 为什么不能叫流失分析？

数据没有事件时间，也没有连续活跃窗口，无法定义多少天未活跃算流失。项目只能分析“是否观察到游玩”和累计时长。

### 如何证明召回策略有效？

当前数据不能证明。需要补齐触达、曝光、启动时间与随机分组，对“大库低启动”用户做 A/B 实验，比较 14 天首次启动率和 7 天游玩时长。

### 数据最大的风险是什么？

一是样本内“是否出现 play”无法替代官方可玩性分类；二是商店元数据精确匹配只覆盖约一半拥有关系；三是价格为 2019 年快照，不能解释历史购买行为。
