# 简历项目表述

## 推荐项目名称

**Olist 电商经营与支付绩效分析｜Python、SQL、Excel、Power BI**

## 简历精简版

基于 Olist 公开电商数据完成 96,211 笔已送达订单的端到端分析，使用 Python/pandas 清洗并连接订单、商品、支付、评价、客户和卖家多表，构建 GMV、AOV、主支付结构、履约、差评、成熟 cohort 复购与供给集中度指标，并落地 SQLite/SQL、6 页 16 图 Excel 看板、15 页 19 图业务汇报及 Power BI 星型模型与 DAX 指标。识别晚到订单与低评分/差评的显著关联（差评率 53.98% vs 9.17%）、成熟 cohort 复购偏低（2.28%）及地区/品类/卖家集中，并提出履约预警、复购随机实验和支付异常隔离方案；通过独立证据门禁明确 GMV≠收入、关联≠因果。

## 简历分点版

- 使用 Python/pandas 对 Olist 8 张真实电商交易表进行清洗、去重、日期标准化与多表关联，建立订单级分析宽表、维度表和 SQLite 数据库，覆盖 96,211 笔已送达订单与 93,104 名客户。
- 设计 GMV、AOV、支付对账、晚到率、差评率、成熟 cohort 复购率及地区/品类/卖家集中度指标，使用 SQL 复核订单、GMV 和支付金额，三项聚合残差均为 0。
- 识别晚到订单差评率 53.98%，显著高于准时订单的 9.17%，并将结果降级为关联信号，提出“州×卖家×品类×路线”风险分层、主动沟通与随机试验方案。
- 分析支付与客户结构：信用卡主支付订单占 75.48%，成熟 cohort 复购率为 2.28%；设计复购触达和分期提示实验，明确主支付方式不等于真实流水份额、静态相关不代表增量。
- 输出 6 页 16 图 Excel 可编辑看板、15 页 19 图 PowerPoint 汇报、HTML 证据报告、Power BI 星型模型/DAX 指南及完整项目文档，实现从数据治理到业务汇报的可复现交付。

## 面试 60 秒介绍

这个项目使用 Olist 的真实电商交易数据。我先把订单、商品、支付、评价、客户和卖家等 8 张表清洗并聚合到统一订单粒度，再构建经营、支付、履约、客户和供给五类指标。最重要的发现是，晚到订单的差评率为 53.98%，准时订单只有 9.17%，这是很强的运营关联信号，所以我把履约风险治理放在第一优先级；但我没有把它写成因果，而是提出按州、卖家、品类和路线分层做主动沟通实验。支付侧信用卡主导订单结构，客户侧成熟 cohort 的复购率只有 2.28%，因此后续重点是补齐退款、成本、流量和实验数据，用随机对照验证复购触达与分期策略。我最终交付了 Python 流水线、SQLite/SQL、Excel 看板、Power BI 指南、PPT 和可审计 HTML 报告。

## 面试追问准备

**为什么只看已送达订单？**

为了让 GMV、履约与评价口径一致，避免取消订单进入交易规模。代价是无法分析取消漏斗，所以我在限制中明确说明，并建议补充完整订单状态用于后续漏斗分析。

**为什么 GMV 不等于收入？**

GMV 只是商品价格合计，缺少退款、退货、平台费、税费、成本与收入确认规则。因此项目只把 GMV 用作交易规模，不计算净收入、毛利或 ROI。

**为什么不能说晚到导致差评？**

晚到和差评可能共同受到地区、卖家、品类、承运路线、旺季等因素影响。当前只有观察数据，没有随机分组或充分混杂控制，所以只能说关联。验证方法是对预计超时订单的沟通策略进行分层随机试验。

**90 天复购率如何避免观察窗偏差？**

只保留拥有完整跟踪期的成熟首购 cohort，再按成熟客户人数加权，避免把窗口末期客户错误计为未复购；同时承认窗口左侧可能遗漏更早购买。

**Power BI 如何搭建？**

以订单事实表为中心，连接客户、商品、卖家和日期维表；支付和评价保持独立事实表，通过订单键关联。DAX 统一计算 GMV、AOV、晚到率、差评率、支付份额与复购指标，页面分为经营总览、支付与分期、履约体验、商品区域、客户供给五页。
